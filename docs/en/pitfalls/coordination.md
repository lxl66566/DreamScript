# Coordination, cargo cache, and gates

Working agreements for parallel lanes and the gates that judge a landing.

- One worktree and branch per agent, additive-only root `Cargo.toml` edits, no git in main, the coordinator the only main writer; two lanes in one worktree switch each other off their branch, so move commits with `git cherry-pick`. Never run `cargo fmt` outside your own worktree, since a stray fmt in main rewrites tracked files and breaks merges.
- A lane worktree's private `.cargo/config.toml` must spell `build.target-dir` (a path), never `build.target` (a triple), which fails every cargo command with `could not find specification for target <path>`.
- The shared target dir serves stale fingerprints and phantom artifacts, so a private `CARGO_TARGET_DIR` or `cargo clean -p <crate>` plus a fresh build is the remedy, and a `Cargo.lock` conflict resolves by deleting the file and regenerating it with `cargo check`. Symptoms: a workspace test linking a parallel worktree's rlib, downstream recompiling while a touched upstream stays stale, E0004 on a `Uop` variant no checkout holds, bin-spawning ds-cli tests failing `NotFound` while each passes alone.
- Every corpus-reading test and bench resolves the corpus at run time through the dev-only `ds-corpus-path` crate (compile-time checkout, else a walk up from the test binary to a root holding `conformance/`), and validates the file rather than the directory, or a spawned `ds check` fails `No such file` blamed on its exit code. That crate's rlib bakes its own `env!("CARGO_MANIFEST_DIR")`, so an earlier lane serves its corpus to every worktree until `cargo clean -p ds-corpus-path` rebakes it.
- `DS_BUILD_ID` folds `Cargo.lock` and each bytecode crate's source tree by file path, so a lock change and a source file's add, rename, or move re-key the checked-in `ambient.dsmod` at its 16-byte header alone, the payload staying byte-identical; the ds-cli run-path files (`run_cache.rs` among them) fold by content, so even an edit without a semantic change re-keys it.
- A `rerun-if-changed` path is package-root-relative, so a sibling crate watched as `ds-check/src` (the crates-dir spelling) watches a nonexistent path under ds-cli: cargo records the watch absent and never reruns the build script on sibling edits, and a warm target dir or a build-script output cache replaying an older stdout then serves a stale `DS_BUILD_ID` — the dsmod regenerates with a header only the generating checkout accepts, and the script cache can share artifacts across builds whose bytecode differs. The fold set and the watch set now derive from one list whose spellings `crates/ds-cli/tests/build_identity_watch.rs` pins; when the dsmod gate drifts across checkouts at one commit again, suspect a stale identity first and force a fresh script run by touching `build.rs`.
- The dsmod regenerates last, after every code edit including `cargo fmt`, since fmt edits are content. An `ambient.ds` edit regenerates three artifacts in the identity's order: `ambient.ast` and `ambient.dsi` fold the identity by content and regenerate before the dsmod, or the serve gates (`SourceDrift`) fail until the clean-and-regen sequence runs again.
- The dsmod payload is a pure function of the tree's content, so a lane regenerating over its own pre-merge or dirty tree commits bytes no merged checkout reproduces, which only another lane's clean checkout reports (the byte gate plus the `@std` `HashMismatch` cascade). Regenerate over the merged tree and re-verify a drift report on a clean checkout.
- A payload-stale `ambient.dsmod` (regenerated before a final `ambient.ds` edit) fails outside the drift gates a lib-target run never sees: the package-run e2e refuses at the walk's dep validation (`dependency @std ... linked at <ambient hash> but resolves to content <artifact hash>`) while targeted suite runs stay green, since those gates live in the ds-cli bin test target. Attribute that `HashMismatch` to the checked-in artifact before suspecting the walk.
- The identity and the payload's source hash fold working-tree bytes as-is, so a checkout under `core.autocrlf=true` (the Git-for-Windows installer default) fails the dsmod drift gate on a clean tree, every byte outside the header identical. Keep lanes on `autocrlf=input` (or `false`), and read a same-size byte-gate refusal as line endings.
- An interrupted or parallel nextest run leaves an orphaned test exe locking its output (LNK1104): find the PID by image name and kill it by PID. `target/debug/ds` is shared across worktrees, so run-probes copy it to a private `/tmp` path first.
- A landing from a stale base silently deletes a sibling's just-landed lines, and a `status.md` milestone row is one table line every landing rewrites whole, so after landing, diff each touched doc item and milestone row against the pre-edit HEAD. Verify a claimed residual against merged main before reopening a closed item, since an unrebased worktree re-reports what a landed round already removed.
- A docs-condensing pass dropped binding sub-rules whose only doc home was the deleted sentence (memory-arc's gate conditions and ledger clauses, the compare-eagerness ruling), and only a full audit round restored them: before deleting a clause, grep the repo for another landing spot, and finding none, condense it in place or move it into the pits file first.
- A gate script piping cargo through tail and echoing `$?` reads tail's exit code, so every such green is vacuous: run gate scripts under `set -o pipefail` and capture cargo's own status.
- Two lanes can mint the same next free diagnostic code (DS2037 landed twice, renumbered to DS2038), so a lane minting a code greps merged main and the coordinator renumbers at merge. After every automated merge grep for `refused_by` and diff3 markers: contested hunks leave doubled paragraphs, and a marker inside a code table fails every later compile.
- The one true test gate is `cargo nextest run --workspace --all-features`, since `--all-targets` fails at listing on `harness = false` benches (exit 104); clippy runs `--workspace --all-targets --all-features -- -D warnings`, and a new test file is selected with `cargo test --test <file>`. Every crate inherits the workspace package fields (clippy's cargo lint group fails on missing readme metadata), and CI runs fmt on nightly only.
- A toolchain update lints or reformats landed code, so verify a workspace clippy failure against pristine main (`git stash push -u`, rerun, pop) and write or-patterns nested so fmt and clippy stop fighting. An allocation-counting test reads a process-global counter, so its windows serialize inside the file behind a static Mutex.
- The .dsi serve's application-mint naming can render an ambient impl head's arguments before the post-replay remap lands them, so an ambient-side generic inherent impl over a parameterized collection head (`impl[k, v] map[k, v]`) names the head through the user's reserve atoms at the generation ids. A mint-sequence mismatch at exactly one atom name in `the_served_analyze_matches_a_fresh_analyze` is that serve path.
- An ambient-name landing re-greps its chosen names against the rebased corpus, since a corpus pin landing in between can declare a name the lane already picked and turn a clean typecheck item into a DS2005 exit-1.
- Corpus fatality scoping is `ds check`-only while `ds run` is fully fatal, so a whole-file run golden needs a file whose items are all run-stage; a ruled refusal class lands in its own all-reject file or stays in the feature's e2e suite.
- Close a round by re-measuring every corpus count on merged main, since worktree counts go stale as landings retire errors, and by rebuilding the corpus byte-diff base binary from the worktree's own HEAD, since a shared-cache binary from another commit shows phantom diffs.
- `cargo run --manifest-path fuzz/Cargo.toml` resolves the workspace only in the main checkout, since cargo walks past a worktree root's `exclude = ["fuzz"]` into main's manifest: append a temporary empty `[workspace]` table (revert it after) and run the seed generator with `fuzz/` as cwd.
- Cargo rejects a dev-dependency cycle as hard as a normal one, so moving a module above its consumer's crate moves its consumer-side tests with it; the move also shifts the ambient dsmod's build identity, so it lands with the regenerated artifact.
- An async lane's completion wake can be dropped while its run finishes normally, so a lane silent past its expected end is checked against the run's status and its run-dir `output-0.log` before any re-dispatch; the committed work sits on its branch either way. `git rebase --continue` needs `GIT_EDITOR=true` there, since the shared editor blocks the coordinator's shell.
- Nightly cargo's per-unit layout never removes a replaced `debug/build/<pkg>/<hash>/` unit dir, so `tools/gc_targets.py` owns the sweep: dry-run by default over one or more target dirs, `--days N` fingerprint-mtime cutoff (default 7), `--apply` to delete, `--incremental` also clearing `debug/incremental*` (kache renames it `incremental.kache-auto`) and `debug/tmp` at round close. A wholesale rebuild or kache rehydration rewrites every fingerprint mtime, so a dry-run right after one honestly reads 0 stale.
- Manual `ds run` probes during parallel lanes pin `DS_CACHE` to a private dir the way every harness's `test_cache()` does, and re-verify a one-off anomalous golden under a private cache before calling it a compiler bug. The serve re-validates the artifact's source hash alone, so a compiler rebuild does not re-key a warm entry for an unchanged source — a stale splice served a fixed derive bug's output verbatim (2026-11-21) — so clear the pinned dir between probe rounds after a rebuild. The cache is proven cross-process safe (2026-11-19): every writer persists through a same-directory temp file whose rename is the single visibility step, every serve re-validates the artifact's name and source hash, and an open artifact never mutates under its reader (`crates/ds-cli/tests/run_cache_race.rs`).
- CI stays one workflow file: two files sharing one `name:` share one concurrency group keyed by workflow name plus ref, so the duplicate's `cancel-in-progress` kills the other file's in-flight runs on every PR. A new CI job lands in `.github/workflows/ci.yml`.
