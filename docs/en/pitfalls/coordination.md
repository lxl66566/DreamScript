# Coordination, cargo cache, and gates

Working agreements for parallel lanes and the gates that judge a landing.

- One worktree and branch per agent, additive-only root `Cargo.toml` edits, no git in main, the coordinator the only main writer; two lanes in one worktree switch each other off their branch, so move commits with `git cherry-pick`.
- Verify a claimed residual against merged `main` before reopening a closed item: an unrebased worktree re-reports what a landed round already removed.
- The shared target dir serves stale fingerprints and phantom artifacts, so `cargo clean -p <crate>` plus a fresh build (or a private `CARGO_TARGET_DIR`) is the remedy, and a `Cargo.lock` conflict resolves by deleting the file and regenerating it with `cargo check`. Symptoms: a workspace test linking a parallel worktree's rlib; downstream recompiling while a touched upstream stays stale; E0004 on a `Uop` variant no checkout holds; bin-spawning ds-cli tests failing `NotFound` while each passes alone.
- Every corpus-reading test and bench resolves the corpus at run time through the dev-only `ds-corpus-path` crate (compile-time checkout, else a walk up from the test binary to a root holding `conformance/`), never a baked `env!` join, so a stale lane's binary re-anchors; it validates the file, not the directory, or a spawned `ds check` fails `No such file` blamed on its exit code.
- `ds-corpus-path`'s rlib is shared too and bakes its own `env!("CARGO_MANIFEST_DIR")`, so an earlier lane's build keeps serving that lane's corpus to every worktree until `cargo clean -p ds-corpus-path` plus a fresh build rebakes it; attribute a corpus-gate failure to the diagnostic's path before suspecting a regression.
- `DS_BUILD_ID` folds `Cargo.lock` and each bytecode crate's source tree by file path, so a lock change and adding, renaming, or moving a source file move it identically and re-key the checked-in `ambient.dsmod` at its 16-byte header alone, the payload staying byte-identical. The ds-cli run-path files (`run_cache.rs` among them) fold by content too, so even a no-semantic-change edit re-keys the header. build.rs does not watch the lock, so a warm target dir masks the drift gate until a cold build fails it: regenerate the artifact in the same landing, and `cargo clean -p ds-cli` before regenerating — the regenerator example bakes the same cached build-script identity, so a warm regeneration re-writes the stale header and the gate keeps failing after it — and a private target dir can see `cargo clean -p ds-cli` remove nothing while the build-script output stays cached, so touch `crates/ds-cli/build.rs` (an mtime bump that forces the re-run without changing any identity input) when the clean does not bite. A `cargo fmt` after the regeneration moves the identity again (fmt edits are content), so the artifact regenerates LAST, after every code edit including fmt. An `ambient.ds` edit regenerates three artifacts, and the order is the identity's own: `ambient.ast` and `ambient.dsi` fold the identity by content (only `ambient.dsmod` is exempted as the moving fixpoint), so both regenerate before the dsmod does — a dsmod regenerated before them bakes the stale header and the serve-side gates fail (`SourceDrift`, `the embedded artifact verifies`) until the clean-and-regen sequence runs again, the ast and dsi generators riding ds-stdlib and the dsmod one ds-cli with its clean.
- A payload-stale `ambient.dsmod` (regenerated before a final `ambient.ds` edit, so the module's source hash predates the ambient's own) fails outside the drift gates a lib-target run never sees: the package-run e2e refuses at the walk's dep validation (`dependency @std ... linked at <ambient hash> but resolves to content <artifact hash>`) while targeted suite runs stay green, and the drift gates themselves live in the ds-cli bin test target — attribute that HashMismatch to the checked-in artifact before suspecting the walk, and verify by reading the artifact's module source hash against a fresh `Hash128::compute` of the ambient source.
- The `ambient.dsmod` payload is a pure function of the tree's content, so a lane regenerating it over its own pre-merge or dirty tree commits bytes no merged checkout reproduces — the generating machine never sees the refusal, only another lane's clean checkout does (the byte gate plus the `@std` HashMismatch cascade), and the 2026-11-18 day's mismatched generations cycled in and out across three parallel merges before a clean-tree regen re-keyed them all. The regen always runs over the merged tree, and a drift report against merged main is re-verified on a clean checkout before it is queued, since a lane can report a residual a same-round landing already removed.
- The identity and the payload's source-hash field fold working-tree bytes as-is (no gitattributes pin them), so a checkout under `core.autocrlf=true` — the Git-for-Windows installer default — fails the dsmod drift gate on a perfectly clean tree, the artifact the same length and every byte outside the 16-byte header and the embedded source hash identical. Keep lanes on `autocrlf=input` (or `false`): the committed artifacts are LF-keyed, and a same-size two-block byte-gate refusal on a clean checkout is the line-ending config, not a drifted artifact.
- An interrupted or parallel nextest run leaves an orphaned test exe locking its output (LNK1104): find the PID by image name and kill it by PID. `target/debug/ds` is shared across worktrees, so run-probes copy it to a private `/tmp` path first.
- A landing from a stale base silently deletes a sibling's just-landed lines, and a status.md milestone row is one table line every landing rewrites whole, so a stale merge drops a sentence or folds two rows. After landing, diff each touched doc item and milestone row against the pre-edit HEAD, not only your own hunks.
- A gate script piping cargo through tail and echoing `$?` reads tail's exit code, so every such green is vacuous: run gate scripts under `set -o pipefail` and capture cargo's own status, or check the command's status before tailing its log.
- Two lanes can mint the same next free diagnostic code and collide (DS2037 landed twice, the second renumbered to DS2038), so a lane minting a code greps merged main and the coordinator renumbers at merge with a repo-wide context grep. After every automated merge grep for `refused_by` and `^|||||||` / `^<<<<<<<`: contested hunks leave doubled paragraphs, and a diff3 marker inside a code table fails every later compile. Fold the double into one line and delete the marker.
- Never run `cargo fmt` outside your own worktree, since a stray fmt in main rewrites tracked files and breaks merges, and review `git diff` after an in-lane fmt. A toolchain update also lints or reformats landed code, so verify a workspace clippy failure against pristine main (`git stash push -u`, rerun, pop) and write or-patterns nested so fmt and clippy stop fighting.
- The one true test gate is `cargo nextest run --workspace --all-features`, since `--all-targets` fails at listing on `harness = false` benches (exit 104); clippy runs `--workspace --all-targets --all-features -- -D warnings`, and a new test file is selected with `cargo test --test <file>`. Every crate inherits the workspace package fields (clippy's cargo lint group fails on missing readme metadata) and composes strings with plain `format!`; CI runs fmt on nightly only.
- An allocation-counting test reads a process-global counter, so its windows must serialize inside the file (a static Mutex held for the whole body): a plain `cargo test` shares one process and a racing window answers a false low count.
- The corpus header and its items stay in one order, pinned by `every_corpus_header_aligns_with_its_items`: a count mismatch makes `item_stages` answer None, so the whole file runs unstaged and every leftover reports fatal, and a right-count-wrong-order header passes the positional zip by luck alone.
- The .dsi serve's application-mint naming can render an ambient impl head's arguments before the post-replay remap lands them, so the first ambient-side generic inherent impl over a parameterized collection head (`impl[k, v] map[k, v]`) failed `the_served_analyze_matches_a_fresh_analyze` by naming the head through the user's reserve atoms at the generation ids; the remap pass re-renders every application atom's name over the landed members, so attribute a mint-sequence mismatch at exactly one atom name to that serve path before touching the generators.
- Close a round by re-measuring every corpus count on merged main, since worktree counts go stale as landings retire errors, and rebuild the corpus byte-diff base binary from the worktree's own HEAD, since a shared-cache binary from another commit shows phantom diffs.
- An ambient-name landing re-greps its chosen names against the rebased corpus, since a corpus pin landing in between can declare a name the lane already picked and turn a clean typecheck item into a DS2005 exit-1; judge the discipline on the merged tree, never the branch base.
- Corpus fatality scoping is `ds check`-only while `ds run` is fully fatal, so a whole-file run golden needs a file whose items are all run-stage; a ruled refusal class lands in its own all-reject file or stays in the feature's e2e suite.
- `cargo run --manifest-path fuzz/Cargo.toml` resolves the workspace only in the main checkout, since cargo walks past a worktree root's `exclude = ["fuzz"]` into main's manifest and refuses: append a temporary empty `[workspace]` table to `fuzz/Cargo.toml` (revert it after), and run the seed generator with `fuzz/` as cwd.
- Cargo rejects a dev-dependency cycle as hard as a normal one, so moving a module above its consumer's crate moves its consumer-side tests with it; the move also shifts the ambient dsmod's build identity, so it lands with the regenerated artifact.
- An async lane's completion wake can be dropped while its run finishes normally, so a lane silent past its expected end is checked against the run's status and its run-dir `output-0.log` before any re-dispatch; the committed work sits on its branch either way. The same round lost no work to the Windows round's stall-and-timeout event, and a `git rebase --continue` needing `GIT_EDITOR=true` (the shared editor blocks the coordinator's shell) is the only extra remedy it took.
- Nightly cargo's per-unit layout never removes a replaced `debug/build/<pkg>/<hash>/` unit dir (a lane's ds-lower test binaries alone piled ~20MB per unit-identity change, 7.1GB before the `V:/targets` move), so `tools/gc_targets.py` owns the sweep: dry-run by default over one or more target dirs, `--days N` fingerprint-mtime cutoff (default 7), `--apply` to delete, `--incremental` also clearing `debug/incremental*` (kache renames it `incremental.kache-auto`, so a literal `incremental` sweep misses it) and `debug/tmp` at round close. A wholesale rebuild or kache rehydration rewrites every fingerprint mtime, so a dry-run right after one honestly reads 0 stale — the corpse re-shows only as replaced identities age past the cutoff.
- Manual `ds run` probes during parallel lanes pin `DS_CACHE` to a private dir the way every harness's `test_cache()` does (the default cache root is shared per user across lanes): a seed-growth round once captured a phantom duplicated output line under the default cache that sixteen private-cache reruns never reproduced, so re-verify a one-off anomalous golden under a private cache before treating it as a compiler bug or pinning it. The cache itself is proven cross-process safe (2026-11-19, closing the todo item): every writer under `$DS_CACHE` — the dsmod run cache, the `.dsi` prefix tier, ds-pkg's store — writes its bytes to a same-directory temp file whose persist is the single visibility step (tempfile 3.27's `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` on Windows, `rename(2)` elsewhere; the `AlreadyExists` remove-retry only ever makes the path absent, never partial), every serve re-validates the artifact's name and source hash against its key, and an open or mapped artifact never mutates under its reader (replacements rename new content in), so a torn install cannot serve and the phantom line was the probe harness's own stdout interleaving, not the cache — pinned by `crates/ds-cli/tests/run_cache_race.rs`, whose bounded campaign (210 concurrent rounds cycling process counts 2/4/8 over one shared root, ~6600 racers across six runs plus 24-wide and two-build fleets) never reproduced it with every racer byte-matching the single-process golden under a reader that observed no partial artifact.
