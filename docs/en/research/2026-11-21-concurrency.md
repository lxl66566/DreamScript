# Research memo — concurrency: IO async, CPU parallelism, locks and shared mutation

Date: 2026-11-21. Scope: answers to Q4a (IO/network async server viability), Q4b (rayon-style CPU parallelism), Q4c (locks and shared mutation), grounded in `docs/en/design-decisions.md` (E1-E5, H1-H6, BL-1..7, C4, D1), `docs/en/status.md` (M5 boundary), `docs/en/todo.md` (items 45, 66), `docs/en/tutorial.md` (Concurrency), and the landed substrate in `crates/ds-vm` (`fiber.rs`, `nursery.rs`, `forkpool.rs`, `net.rs`, `claims.rs`).

## What actually exists today (substrate audit)

The fiber substrate is real but there is no scheduler. `crates/ds-vm/src/fiber.rs` defines the full switching vocabulary: a fiber is pool data (segment, per-fiber arena, per-fiber heap store, call chain) with states `Ready / Running / Suspended / Preempted / Dead`, a `ResumePoint` (module version, function, pc), a resumer link, and O(1) switching by three buffer swaps. `crates/ds-vm/src/nursery.rs` states the gap verbatim: "Nothing here schedules: the pool is single-threaded, and the driving discipline is fixed below so every observable follows from spawn order alone" — the join/teardown driver enters children in spawn order and drives each child to death before entering the next. A child can park only at control calls (`fiber_resume`, the nursery joins) or at a host suspension request on a taken backward branch; the driver re-enters parked children with the bare `PLATFORM_NONE` bounce tag. `crates/ds-vm/src/net.rs` serves net ops over plain blocking `std::net::TcpStream` with bounded timeouts, so any net op blocks the single VM thread outright. The fork-join pool (`forkpool.rs`) is the only multi-thread execution: whole fibers move as `ForkCargo` to youpipe scoped workers over per-thread cached worker VMs, gated to children whose entry frames hold exclusively scalar words. So: fibers, parks, resume points, cancellation flags, and a worker pool all exist; a run queue, a reactor, and any notion of "run some other ready fiber while this one waits on IO" do not.

## Q4a — IO/network async: can this design serve a high-performance server?

### Short answer

Not today, and the missing pieces are runtime rulings rather than language redesign: a scheduler (run queue plus park-on-world-op discipline) and a reactor behind the net capability. The E1 capability/handler architecture is exactly the right seam for the change; the blocking-style fiber model is the same substrate Go and Loom proved at scale.

### 1. Event-loop integration behind the net capability — prior art

Go. The canonical existence proof for "blocking-style code over OS async IO." A goroutine that calls a blocking network op parks; the fd is registered with an integrated netpoller (epoll/kqueue/IOCP in `src/runtime/netpoll.go`); when the run queue is empty a P (logical processor) polls ready fds and unparks their goroutines; sysmon retakes Ps stuck in blocking syscalls; since Go 1.14 goroutines are asynchronously preempted. The event loop and the scheduler are one component, which is why no `await` ever appears. Cost per goroutine: ~2 KiB initial stack, tens of millions runnable.

Java Loom. Virtual threads (final in Java 21) are heap-allocated stack chunks that mount on a ForkJoinPool carrier and unmount on any JDK blocking call — the JDK's own socket layers were rewritten internally to poll so the old `Socket.read` parks a continuation instead of an OS thread. Lessons for DreamScript: (a) retrofitting parking into a "blocking" API surface is feasible without changing user code; (b) pinning is the one permanent hazard (synchronized blocks, native calls — DreamScript already rules the second: a blocking foreign call pins its fiber, H5); (c) throughput is roughly platform-thread parity — Loom's win is connection count (millions of virtual threads), not req/s; the six-preview history of StructuredTaskScope confirms DreamScript's bet that the nursery is the hard part, and DreamScript already has it.

BEAM. Preemptive per-reduction-count scheduling (~4,000 reductions per slice), per-scheduler run queues, IO through poll sets and port/dirty schedulers, and copying message sends. Throughput per core is an order of magnitude below Go/tokio for raw HTTP, but it holds soft-real-time tail latency under millions of concurrent connections (WhatsApp's famous 2M connections per node). The relevant lesson: if the language's latency and isolation story is the selling point, per-core req/s is not the metric; DreamScript's per-fiber heaps and non-atomic RC give it the same isolation shape with less copying.

Rust tokio. Stackless colored tasks (the opposite design) on a work-stealing scheduler with a mio reactor driver thread. Included because it sets the performance ceiling and shows what the reactor interface looks like (registration, waker/unpark). Its lesson is that the scheduler and reactor are where the engineering budget goes; the task representation (stackful vs stackless) is secondary.

Rough HTTP server ballparks (TechEmpower-style plaintext/JSON, multi-core, orders of magnitude — treat as ±2x): Go net/http ~ 1-3M req/s plaintext, ~1M req/s simple JSON; top tokio-based frameworks ~ 2-7M plaintext; Loom-based serving ≈ platform-thread throughput for IO-bound work (millions plaintext in tuned frameworks), its advantage being concurrency count and tail behavior under connection churn; BEAM ~ 100-500k req/s for simple HTTP handlers, with best-in-class p99s at high connection counts. Any M:N fiber runtime that parks on readiness instead of blocking threads lands in the same regime; the differentiators become per-request CPU cost and tail latency, which is where DreamScript's next problem lives.

### 2. What the tier-1 interpreter costs a server, and where the holes are

Holes, precisely: (a) there is no scheduler — nothing picks the next fiber when the running one parks, and nothing ever parks on a world op; (b) net ops are OS-blocking calls on the single VM thread, so today one `net_connect` stalls every fiber in the VM; (c) there is no reactor — no fd readiness source, no wakeup delivery, no timer wheel behind the timer capability; (d) cancellation of a fiber parked on IO is unruled (E5 observes cancellation at resume points, so a reactor-delivered cancel sentinel fits the existing resume-shaped preemption point, but nobody has written that ruling); (e) TLS today is blocking rustls, though rustls is a synchronous state machine that can ride a non-blocking socket, so this is plumbing, not architecture.

Interpretation overhead. Tier 1 targets 3-10x of C. For an IO-bound server the reactor and syscall path dominate when handler bodies are thin (parse request, read a cache, write bytes); there, a 3-10x interpreter penalty on a small handler is survivable — the ceiling is set by connections held and wakeup cost, and the per-fiber memory footprint (chunked segments + per-fiber heap store) is larger than a goroutine's 2 KiB but small enough for tens of thousands of fibers. For anything with real per-request compute — routing, JSON encode/decode, template rendering, header normalization — the interpreter cost is on the critical path of every request. If a Go-class runtime spends ~50-100 us of CPU per trivial JSON request, a 3-10x interpreter lands at a realistic 5k-50k req/s per core for a JSON endpoint: two to three orders of magnitude below Go/tokio, adequate for admin APIs, CLIs, dev servers and scripting-internal servers, not competitive as a general-purpose high-performance server runtime at tier 1. CPU-bound handler logic multiplies the same 3-10x by definition. Conclusion: the design can serve a high-connection-count IO-bound server at tier 1; "high-performance" in the req/s sense waits on tiers 2/3 exactly as much as every other workload does.

### 3. Rulings needed to make net ops fiber-parking, and whether E1 already provides the seam

E1 provides the seam, almost completely. World ops already route through the platform tables (`platform "std" provides <console, fsys, net, time>`) behind a host-installed handler; an op's implementation is a platform choice, not a language fact, so swapping a blocking net face for a parking one requires zero syntax or type-system change. The fiber machinery already has the shape the swap needs: `FiberState::Suspended` with a `ResumePoint` after the parking call and a resumer identity, plus the `PLATFORM_NONE` bounce convention the nursery driver uses to re-enter parked children — a reactor wakeup is exactly "resume this fiber at its park with the op's result word." The genuinely new rulings are: (1) a run queue and a drive discipline — when the running fiber parks on a world op, who runs next, and what is the fairness/starvation contract; (2) the reactor interface — registration of fd readiness and timer expiry, delivering resumes, including cross-thread wakeup if the pool later runs fibers on multiple threads; (3) parked-on-IO cancellation — the reactor deregisters and delivers `PLATFORM_CANCELLED` at the resume-shaped point, per the 2026-11-12 amendment pattern; (4) the determinism boundary — "every observable follows from spawn order" can survive only for the fork-join drive, since IO completion order is external; sibling interleaving at world-op parks must be ruled unspecified (this is the ruling Q4c depends on); (5) whether the multi-thread executor (fibers, not just fork children, on worker threads) exists at all before 1.0 — a single-thread reactor over the existing pool already serves a real server and keeps every fiber on its own heap with non-atomic RC untouched.

## Q4b — rayon-style CPU parallelism

### What exists and what the gap to rayon-class is

`par_map`/`par_reduce` exist as deterministic sequential slices; the pool sits behind the host opt-in `Vm::enable_fork_pool`, is byte-identical to the sequential drive, and admits only children whose entry spans are exclusively scalar words (a `Ref` word names a foreign heap the worker cannot route, so Ref-carrying children fall back to the sequential interlock on the host). Item 45 ranks the residuals: the immutable-borrow admission (ruled 2026-11-15 — pooled children may read foreign immutable `Ref` entry words without touching counts, the join adopting on the host with one inc per surviving reference) is an M-tier round behind 0.1; `par_reduce` parallelism waits on the associativity proof (the `associative` marker trait was rejected, so the fold is sequentially defined until a proof story exists); worker-grained chunking rides the ClaimWindow seam; the trivial-body transfer overhead (~3.1x the sequential slice, with the two-child bar) bounds what pooling can win.

Measured against rayon: rayon is per-worker work-stealing deques, recursive splitting to a grain size, tree-structured parallel reduce over associative combines, and free shared read-only access (`&T` borrows) across threads. DreamScript's equivalents line up cleanly: work stealing exists at the youpipe layer (workers steal back to the joining thread) but there is no adaptive chunking — splitting is one child per element, which is why transfer overhead dominates trivial bodies; parallel reduce is blocked on the associativity question rather than on machinery; shared read-only access is precisely the immutable-borrow admission; per-worker arenas already exist by ownership transfer (the whole fiber — segment, arena, heap store, ledger — moves as cargo, so every worker context is arena-equipped by construction). So the gap is exactly item 45's list; nothing architectural is missing. The one structural difference from rayon is deliberate: rayon threads share one heap and pay synchronization; DreamScript moves whole fibers and keeps non-atomic RC sound by confinement, which costs the copy-in/copy-out per child and is why chunking matters more here than there.

### Is sequential-contract-then-pool sound?

Yes — it is the strongest available architecture for a tiered runtime. The sequential drive is the semantic definition; the pool is a pure optimization that must answer byte-identically, so every future scheduler change is differential-testable against the contract (the differential pins are already queued in item 45). This is the same shape as rayon's sequential fallback and as deterministic-parallelism research runtimes, and it means bugs in the pool can never change program meaning. The cost is that the pool's gate must be conservative (scalar-only today), which is the right side to err on.

### Realistic speedups and honest sequencing

At tier-1 speed (3-10x of C), a numeric kernel element body is interpreter-dominated, so pooling gives at most a near-linear speedup up to worker count for non-trivial bodies, minus the ~3.1x trivial-body transfer overhead — say 3-6x on 8 workers for real workloads. But the absolute throughput is still 3-10x below single-threaded C: parallel-8 DreamScript ≈ 0.5-2x of one C thread. CPU parallelism multiplies a slow scalar; it does not fix it. Recommendation: land the item-45 residuals that complete the semantics (immutable-borrow admission, chunking, the `par_reduce` associativity story) because they are correctness/contract rounds that make the shipped feature honest, but invest no tuning effort in the pool and set no performance expectations for CPU-bound numeric work until tier 2 (copy-and-patch, target 1.5-3x) and ideally tier 3 land. The sequenced priority for serving numeric users is tier 2 first, pool widening second — the reverse of effort intuition, because the pool's wins are bounded by cores while the interpreter penalty is paid by every element on every worker.

## Q4c — locks and shared mutation

### The design's current answer, and what the tutorial example actually relies on

D1 rules that exclusion-window mutation is the only channel and shared mutation is unrepresentable; E3 makes race-freedom a static theorem for fork-join. What nursery siblings actually share today is: nothing concurrently. The nursery driver is sequential — each child is driven to death before the next is entered — and the parent is parked at the join for the children's whole lifetime. The tutorial's `pages.list_push(p)` inside `spawn` bodies is safe by temporal construction: each child holds its `mut` window over the captured parent binding only while it alone runs, the parent's own window is suspended at the nursery block, and the parent reads `pages` only after the join. Every observable follows from spawn order alone, so the pushes land in spawn order, deterministically. This is safe today — but it is load-bearing on the sequential drive, not on any interleaving-safe rule. The moment Q4a's scheduler lets a child park on IO and a sibling run, two children each holding a live `mut` window over one captured binding would interleave their pushes in external completion order, and the D1 theorem ("statically exclusive, zero runtime checks") quietly stops describing execution. This hole must be closed by ruling before any IO scheduler lands, not discovered after.

### What mechanisms shared state would need

(1) Nursery-sibling mutable state. A Rust-style `Mutex<T> + Arc<T>` is structurally inexpressible here: it requires shared ownership (atomic RC — refused by C4) and shared mutable access (refused by D1), so a mutex would guard a state shape the language cannot construct. Pony-style reference capabilities (iso/trn/ref/box/val/tag) are a whole second ownership calculus — exactly the learning-cost and error-rate profile the charter's ownership endgame (C1, ruled 2026-11-17: no escape hatch reserved) rejected. The two precedents that fit linear data are Erlang/BEAM and Inko: no shared memory at all, values move between processes (a linear value is sendable by construction — Inko's `uni T` is the same observation), and coordination is message passing. Go's channels are the same discipline over a shared heap with a GC to forgive the aliasing. DreamScript's linear/immutable substrate already contains both halves of message passing: sending consumes the value (affine move), receiving returns ownership.

(2) Channels as the intended answer. The todo already points here: "a bounded-channel library type parks on the fiber substrate, both behind 0.1" (item 45). A bounded channel is a library type whose buffer lives in one designated heap; send/recv are world-adjacent ops that park the calling fiber when full/empty and resume a waiter on the other side. Note the dependency: channels require the Q4a scheduler (parking and waking), so Q4c's mechanism rides Q4a's ruling. Actor-style mailboxes are the same type with per-fiber ownership of the queue; supervision is already ruled a library pattern (E4's let-it-crash).

(3) Atomic RC and the claim ledger. Atomic RC was deliberately refused (Perceus non-atomic counts, thread-confined through the fork-side transfer, E3/C4). The claim ledger is the cross-heap accounting channel: every count a frame acquires enters its fiber's ledger, releases leave it, and C4's count-funnel ruling already permits a foreign heap to post requests drained to quiescence — which is exactly the mechanism a channel payload transfer needs (the claim moves with the value; no atomic inc ever happens). The ledger is the reason message passing over per-fiber heaps needs no GC and no atomic counts.

### Recommendation on primitives

v1 vocabulary: nursery/spawn/cancel (shipped), `par_map`/`par_reduce` (shipped, sequential-contract), one bounded-channel/mailbox library type with `send`/`receive` that park, and `firstof`/`select`-style combinators over channels plus the timer capability (E5 already names `firstof`/`interleave` as library combinators). Post-1.0: supervisors, restart strategies, and any structured mailbox taxonomy as libraries. Locks: never. D1 makes shared mutation unrepresentable, so a lock primitive would guard nothing expressible; introducing one would either be dead weight or would smuggle shared-mutable cells in through the back of the ownership endgame. The honest statement for the author: "is there a locking concept" — no, and the design is coherent precisely because there is nothing for a lock to lock; "what if two fibers modify the same thing" — today they cannot (the checker refuses the shape, and the sequential drive would serialize it anyway), and after the IO scheduler lands the checker must refuse it actively rather than rely on drive order.

## Recommended rulings

Candidate rulings for the author, each independently adoptable:

1. **R-IO-1 (scheduler).** The VM gains a run queue and a park-on-world-op drive discipline: net and time ops park the calling fiber with a `ResumePoint` after the op instead of blocking the thread; the drive runs the next ready fiber; fairness is FIFO with the existing backward-branch preemption points. The single-thread executor ships first; a multi-thread fiber executor is post-1.0.

2. **R-IO-2 (reactor behind the capability).** `platform "std"`'s net face is implemented over a reactor (epoll/kqueue/IOCP; io_uring a later swap), installed through the existing E1 capability seam with zero syntax or type-system change; blocking semantics remain a platform choice for embedders, never a language fact. TLS rides rustls's synchronous state machine over non-blocking sockets.

3. **R-IO-3 (parked-IO cancellation).** A fiber parked on a world op observes nursery cancellation by reactor deregistration delivering `PLATFORM_CANCELLED` at the resume-shaped preemption point, extending the 2026-11-12 amendment; teardown then runs the existing frame walk and deinits.

4. **R-IO-4 (interleaving boundary).** Spawn-order determinism ("every observable follows from spawn order alone") is guaranteed only within the pure fork-join drive; once a child can park on a world op, the relative order of sibling observables is unspecified. Correspondingly, a spawn body may not hold a `mut` window over any binding that outlives the nursery block once the IO scheduler lands — nursery results flow through the children answer spans (the existing `JoinOutcome` channel) and combinator-style collection; the tutorial's `pages.list_push(p)` pattern migrates to collecting child answers in spawn order. Prefer making the refusal permanent, so the sequential drive never carries a latent miscompilation.

5. **R-PAR-1 (sequencing).** The fork-join residuals of item 45 (immutable-borrow admission, ClaimWindow chunking, the `par_reduce` associativity story) are landed as contract-completing rounds, but pool performance investment and any CPU-parallelism performance claims wait on tier 2 (and preferably tier 3); CPU parallelism multiplies the interpreter's 3-10x penalty and is not a user-visible lever before the JIT tiers.

6. **R-LOCK-1 (channels, not locks).** No lock, mutex, or atomic primitive enters the language, permanently: D1 makes shared mutation unrepresentable, so a lock would guard nothing expressible. Inter-fiber shared state is one bounded-channel/mailbox library type whose buffer lives in one owning heap, with payload claims transferring through the existing ledger and C4's foreign-post funnel — no atomic RC, ever.

7. **R-LOCK-2 (v1 concurrency vocabulary).** v1 = nursery/spawn/cancel, `par_map`/`par_reduce` under the byte-identical sequential contract, the bounded channel, and `firstof`/timeout combinators over channels plus the timer capability. Supervisors, restart strategies, and mailbox taxonomy are post-1.0 libraries over the same substrate.
