# Q5 — Error taxonomy granularity and user-friendliness

Research memo, 2026-11-21 basis. Sources: `docs/en/design-decisions.md` (B5, E4, H5.5), `docs/en/tutorial.md` ("Types are sets", "Errors and extraction"), `crates/ds-stdlib/src/ambient.ds`.

## 0. What exists today

The ambient predeclares the failure taxonomy (`ambient.ds`):

```ts
pub tag io_err
pub tag parse_err
pub tag utf8_err
pub enum net_err {
  timeout
  refused
}
```

Key facts from the source:

- `io_err`, `parse_err`, `utf8_err` are bare unit tags. They carry no payload: no message, no OS code, no position. `parse_json` answers a bare `parse_err` and the ambient comment says explicitly "the offending position is not carried".
- `net_err` is the one two-case enum, and the runtime has an "error-class mapping": the net natives' internal failure discriminants land on the `net_err` case the class names. The file surface has no equivalent mapping — every file failure collapses onto the single `io_err` tag even though the platform handler knows more (the total spelling prints `io error: <msg>`, so a human-readable message exists in the runtime and is then dropped from the typed value).
- Propagation is B5/E4: `?` is checked containment — the enclosing return union must contain each propagated member, no implicit conversions. `.err(h)`/`.ok(h)` are set-difference-typed. H5.5 rules user and library errors are ordinary declared types.

## (a) Is `io_err` granular enough?

No, not for real programs. The moment a CLI tool wants "create the file unless it already exists" or "report permission problems differently from a missing path", a single `io_err` tag forces string-parsing of a message it does not even carry. Today the only recovery move is `.err((e) => fallback)` over the whole class.

### Cross-language comparison

- **Rust `std::io::ErrorKind`** — ~40 variants (`NotFound`, `PermissionDenied`, `ConnectionRefused`, `AddrInUse`, `TimedOut`, `AlreadyExists`, `InvalidInput`, `UnexpectedEof`, ...), plus a raw OS error payload and a message. The variant set exists because callers genuinely branch on maybe a dozen of them (`NotFound` and `PermissionDenied` dominate real code; the long tail is matched with `_`). Cost of the width: an unstable enum and a large match surface most programs never use.
- **Python `OSError`** — an errno-keyed subclass tree (`FileNotFoundError`, `PermissionError`, `TimeoutError`, ...), each instance carrying `errno`, `strerror`, `filename`. Fine granularity arrives through inheritance; the cost is a deep hierarchy and the entangled identity/data/behavior the project's design philosophy rejects.
- **Go** — one `error` interface, sentinel values (`fs.ErrNotExist`) plus `syscall.Errno`, matched with `errors.Is`/`errors.As`. Granularity is opt-in per package, but the mechanism is runtime value matching — exactly the stringly/dynamic checking DreamScript's charter rules out in favor of compile-time sets.
- **Zig error sets** — the closest structural analogue to DreamScript. Error values are bare names; sets merge structurally (`A || B`), inference produces the exact set, and coercion into a wider set is free. The observed ergonomics: fine-grained error names are nearly free to declare and to compose, and nobody writes `catch` ladders over 40 kinds — they handle one or two and propagate the rest. The known pain is the opposite of Rust's: error names carry no payload and no message, which Zig offsets with debug-mode error return traces.
- **Java checked exceptions** — the cautionary tale: a nominal tree where every layer must re-declare, producing catch-all swallowing. DreamScript's union members with `?` containment are strictly better here because the "re-declaration" is a set union the checker verifies rather than a throws clause the author maintains by hand.

### Recommendation: union of unit tags under one alias

`net_err` already shows the shape the runtime supports (an enum with per-class cases). For `io_err` the recommendation is to go one step further than the enum and use the language's own strength — set-theoretic unions — the way Zig uses error sets:

```ts
tag not_found
tag permission_denied
tag already_exists
tag timed_out          // shared with net if the class is genuinely shared
tag unexpected_eof
tag io_other           // the catch-all floor
type io_err = not_found | permission_denied | already_exists | timed_out | unexpected_eof | io_other
```

Rationale:

1. **Aliases make width free.** A signature spells `-> t | io_err` exactly as today; `?` containment is set containment, so `read_file` answering `not_found` propagates through any union that contains the alias's members. There is no ergonomic penalty for granularity at the declaring site, and none at the propagating site. This is the decisive advantage over a Rust-style wide enum, where one more variant is one more arm in every exhaustive match: here a handler matches `not_found => ...` and lets `_` or `.err(h)` absorb the rest.
2. **Precision is composable, not bureaucratic.** A function that can only fail one way declares `-> t | not_found` and callers see it; the tutorial already models this (`type fetch_err = timeout | refused | parse_error`). An enum (`io_err` as one nominal atom with cases) cannot express "only not_found is possible" — every consumer must handle the whole enum.
3. **Enum vs union-of-tags.** An enum gives one tag identity and slightly tidier exhaustiveness messages ("missing: already_exists | io_other" works either way). A union alias of unit tags allows independent per-tag extension and per-function precision, and matches B3's `tag x;` machinery with zero new concepts. The cost: editing the alias is a semver-relevant change (acceptable — rapid-break until 1.0, A3), and tags pollute the type namespace (mitigated by the `io_`-prefix-free short names being ordinary nominal atoms; F9 keeps them out of the value namespace unless constructed).
4. **Keep the set small and branchable.** Rust's 40 kinds are an accident of POSIX errno coverage, not a design target. Discriminate only what a program would branch on: roughly `not_found`, `permission_denied`, `already_exists`, `timed_out`, `refused`, `addr_in_use`, `unexpected_eof`, `invalid_input`, plus one `*_other` floor per domain. That is ~10 atoms total across io/net, not 40. The natives' existing error-class mapping extends directly; classes the platform cannot discriminate portably fold into `io_other`.

The same treatment applies to `parse_err`: keep one tag for shape failures but consider a sibling split only where callers branch (e.g. `parse_eof` is rarely worth it — recommend not splitting). `utf8_err` stays a single tag; nobody branches on UTF-8 failure classes.

### Wide unions vs one coarse tag — ergonomics verdict

The feared cost of fine granularity — every intermediate function re-listing every member — does not materialize, for three reasons: (1) the alias is one spelling; (2) `?` containment checks membership, not spelling; (3) `.err(h)` handlers subtract by set, so handling `not_found` out of `io_err` leaves the remainder type `io_err - not_found` printed as such. The one real cost is signature drift when the alias grows (a new member silently flows through every `?` chain — which is semantically correct anyway) and exhaustiveness breakage for consumers who matched all members without a catchall (the intended, desirable breakage — set-difference diagnostics name the new member). Verdict: wide unions under aliases are strictly more ergonomic than a coarse tag for any program that branches on failure classes, and no worse for programs that do not.

## (b) What should an error carry?

### Survey

- **Rust anyhow/thiserror.** thiserror derives `Display` + `Error::source` chains on nominal error types — errors are data with a reporting interface. anyhow adds context stacking and a captured backtrace for the "propagate to the top and print" path. The lesson: the *chain* and the *backtrace* serve debugging of unexpected failures; expected failures need only a message.
- **Zig.** Error values are bare names; debug builds keep an error return trace (captured at each `errdefer`/return site) as a runtime-side channel, not part of the value. The lesson: the trace belongs to the runtime/diagnostic layer, not the error datum.
- **Gleam.** `Result(a, e)` with user-declared error types, typically custom enums with payload fields; reporting is pattern matching plus `string.inspect`. The lesson: when errors are ordinary data, the language needs no error-specific reporting machinery at all.

### Recommendation for v1

1. **Error values are data; `show` suffices.** H5.5 already rules errors are ordinary declared types, and the `show` derive exists. A failed program prints its error through `show`/`str`; no error-specific display trait is needed. This matches the philosophy that compile-time structure beats runtime reporting machinery.
2. **No backtrace on error values.** Errors-as-values model *expected* failures; a backtrace per error construction would tax the hot path B5 prices at "one predicted branch". Reserve traces for traps: the `Die` ruling already carries a message out to the drive, and any future trap-trace work belongs there (M9 hardening), not in the value layer.
3. **Payloads per member, decided before 1.0, not after.** E2 already supports payloaded members riding the nursery boundary ("a payloaded member riding its whole value out"). The one payload with clear v1 justification is **position/span on `parse_err`** — the ambient itself flags that the JSON reader drops the offending position, which makes `parse_err` useless for any tooling-grade diagnostic (and DreamScript's own toolchain promises two-span diagnostics; a stdlib that cannot locate a parse failure contradicts the tooling commitments). Recommend: before 1.0, walk the ambient taxonomy and rule per member whether it carries a payload struct (e.g. `parse_err { msg: string, at: int }` or stays bare), because turning a bare tag into a payloaded case is a breaking change cheap only during rapid-break. Default: bare tags; payload only where the consumer demonstrably branches on or reports the payload (parse position; possibly an OS message string on `io_other`).
4. **A message field is not generally worth it.** The runtime already prints `io error: <msg>` on the total-spelling halt, which covers the script path. For typed error values, an OS message string on every failure is allocation on a cold-but-not-free path; recommend `io_other` optionally carrying it, the branchable tags staying bare.

## (c) A standard `err` interface?

**Recommend: no dedicated error trait in v1.** The reporting interface is `show`, and E4's extraction family (`.err`/`.ok`/`map_err`) is already the handling interface — both are ordinary traits/functions over unions, not an error hierarchy. A mandatory `err` trait would recreate Java's coloring pressure (every library error forced into one interface) for no compile-time gain, since `?` and containment never consult an interface — only set membership.

The one defensible addition is a *convention*, not a mechanism: an @std `describe` trait (one member `fn describe(self) -> string`) for user-facing messages where `show`'s structural rendering is too raw, so a top-level CLI handler can print `describe(e)` uniformly over the taxonomy. This is optional, library-level, and additive; if adopted it belongs in @std with blanket-ish impls for the ambient tags, and the tutorial should show it once. Do not gate propagation, printing, or nursery error-unioning on it.

## Summary of recommendations

1. Split `io_err` into ~6–8 unit tags under a `type io_err = ...` alias; extend `net_err` the same way (`addr_in_use`, `reset`, ...); keep `utf8_err` single; keep `parse_err` single but rule on a position payload before 1.0.
2. Errors stay payload-free data by default; payloads only where branched on or reported (parse position, maybe OS message on the catch-all). No backtraces on values; traces belong to the trap/Die layer.
3. No standard `err` trait; `show` (and optionally an @std `describe` convention) is the whole reporting interface.
