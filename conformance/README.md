# Conformance corpus

The DreamScript conformance corpus: the frozen archive's seed programs (`archive/design/` catalogs) ported to the decided surface syntax per the M1 work items of `docs/en/implementation-plan.md`. The runtime encodings (catalog 07-runtime) are covered by the ds-abi/ds-vm hand-assembled fixtures instead. Every future bug regression lands in this directory as a new item or a new file; a regression never lives only in a unit test. Every `.ds` file sits at `ds fmt`'s canonical form (the CI ds-fmt job gates the corpus alongside examples/ and the benchmark kernels), so run the formatter after editing one; the header blocks and separator lines are preserved verbatim.

## Package fixtures

The multi-package corpus beside the single-file files: one directory per fixture under `packages/`, carrying the consumer package root `app/` (its `ds.pkg` manifest, the `main.ds` entry with the same `// items:` header grammar as every corpus file, and any same-package member files) beside an optional producer package root the manifest's path dep names (`[deps.@name]` with `path = "../name"`, the workspace spelling). The gate runs in `crates/ds-cli/tests/conformance.rs`'s package-fixture test, in deterministic fixture-name order: a fixture declaring no producer root checks through `ds check` beside its members (the header's staged rejects print, never fatal, one diagnostic per reject item), and a fixture carrying a `run.golden` runs through `ds run` and byte-pins the file exactly like the single-file goldens — a cross-package fixture's run is its own check, the consumer's compile typing against the linked surface the resolution serves. A fixture without a golden stays on the check leg alone: a reject-staged fixture the run would refuse, or a check-only one whose surface sits outside the M3 lowering contract (the top-level-value boundary the single-file corpus records for toplevel_consumption.ds — a member's top-level const is not readable at runtime, DS4009). Producer sources are plain package members (no header); A same-package member file may carry the `// items:` header too, and the gate stages it exactly like the entry's (a member without one stays a plain source file, fully fatal under the composed check), the reject count reading the whole package. Producer sources are plain package members (no header); a fixture entry's imports stage `m7`, their constructs the package milestone's own.

## Header format

Every `.ds` file starts with a header comment block that ds-parse tests parse mechanically:

```text
// source: <record reference>
// purpose: <one line>
// items:
// <item-id>: stage: <stage-expression>
```

Rules: exactly one `source` line and one `purpose` line, one `items:` line, then one item line per top-level item, listed in source order. An item-id is `[a-z0-9_-]+`: the declared identifier when the item declares one, otherwise a descriptive slug (for example `impl-json-int`, `ds-pkg-manifest`). A stage-expression is one of the vocabulary entries below; `reject` and `unresolved` carry free text after the keyword. Items with stage `unresolved` are preserved in the body as commented-out code and are skipped by every runner; items with stage `reject` are live code that must parse.

## Stage vocabulary

| Stage | Binds at | Meaning |
|---|---|---|
| `parse` | M1 | item must parse; no further expectation yet |
| `typecheck` | M2 | item must typecheck under ds-check (syntax_ts_heart.ds's byte literal `b'x'` types through the ambient's `tag byte` with no user declaration) |
| `run` | M3-M5 | item must execute with correct output once its file's run-binding milestone lands (see file list) |
| `m6` | M6 | item needs derives, comptime evaluation, or reflection |
| `m7` | M7 | item needs modules, packages, or FFI |
| `reject <what>` | M2 unless the text names later | negative item: must parse, then produce the described error |
| `unresolved: <why>` | never | spelling genuinely undecided in the record or out of scope for v1 |

Cumulation rules: every item except `unresolved` must parse from M1. Items staged `typecheck` or `run` must typecheck from M2. Items staged `run` execute from their file's run-binding milestone. Items staged `m6` or `m7` are exempt from the typecheck and run gates until their own milestone, because their constructs (comptime parameters, extern declarations, imports) do not check earlier. Golden output files land together with the milestone that first runs each file.
